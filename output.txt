    <p>
      So far, our browser sees web pages as a stream of open tags, close
tags, and text. But HTML is actually a tree, and though the tree
structure hasn’t been important yet, it will be central to later
features like CSS, JavaScript, and visual effects. So this chapter adds
a proper HTML parser and converts the layout engine to use it.
    

    <h1>
      A Tree of Nodes
    

    <p>
      The HTML tree
      <span>
        
        <span>
          This is
the tree that is usually called the DOM tree, for 
          <a
href="https://en.wikipedia.org/wiki/Document_Object_Model">
            Document
Object Model
          . I’ll keep calling it the HTML tree for
now.
        
       has one node for each open and close tag pair and a
node for each span of text.
      <span>
        
        <span
class="note">
          In reality there are other types of nodes too, like
comments, doctypes, 
          <code>
            CDATA
           sections, and processing
instructions. There are even some deprecated types!
        
       A
simple HTML document showing the structure is shown in Figure 1.
    

    <div>
      

      <figure>
        

        <img>
        

        <figcaption>
          Figure 1: An HTML document, showing tags,
text, and the nesting structure.
        

      

    

    <p>
      For our browser to use a tree, tokens need to evolve into nodes. That
means adding a list of children and a parent pointer to each one. Here’s
the new 
      <code>
        Text
       class, representing text at the leaf of the
tree:
    

    <div>
      
      <pre
class="sourceCode>

            <a>

          <span>

    <p>
      I added a 
      <code>
        children
       field to both 
      <code>
        Text
       and

      <code>
        Element
      , even though text nodes never have children, for
consistency.
    

    <p>
      Constructing a tree of nodes from source code is called parsing. A
parser builds a tree one element or text node at a time. But that means
the parser needs to store an 
      <em>
        incomplete
       tree as it goes. For
example, suppose the parser has so far read this bit of HTML:
    

    <div>
      
      <pre
class="sourceCode>
        
        <code>
          
          <span>
            
            <a>
              
            
            <span>
              <html><video></video><section><h1>
            This is my webpage
          
        
      
    

    <p>
      The parser has seen five tags (and one text node). The rest of the
HTML will contain more open tags, close tags, and text, but no matter
which tokens it sees, no new nodes will be added to the

      <code>
        <video>
       tag, which has already been closed. So that
node is “finished”. But the other nodes are unfinished: more children
can be added to the 
      <code>
        <html>
      ,

      <code>
        <section>
      , and 
      <code>
        <h1>
       nodes,
depending on what HTML comes next—see Figure 2.
    

    <div>
      

      <figure>
        

        <img>
        

        <figcaption>
          Figure 2: The finished and unfinished
nodes while parsing some HTML.
        

      

    

    <p>
      Since the parser reads the HTML file from beginning to end, these
unfinished tags are always in a certain part of the tree. The unfinished
tags have always been 
      <em>
        opened
       but not yet closed; they are
always 
      <em>
        later in the source
       than the finished nodes; and they
are always 
      <em>
        children of other unfinished tags
      . To leverage these
facts, let’s represent an incomplete tree by storing a list of
unfinished tags, ordered with parents before children. The first node in
the list is the root of the HTML tree; the last node in the list is the
most recent unfinished tag.
      <span>
        
        <span
class="note">
          In Python, and most other languages, it’s faster to add and
remove from the end of a list, instead of the
beginning.
        
      
    

    <p>
      Parsing is a little more complex than 
      <code>
        lex
      , so we’re
going to want to break it into several functions, organized in a new

      <code>
        HTMLParser
       class. That class can also store the source code
it’s analyzing and the incomplete tree:
    

    <div>
      
      <pre

          <span>
            
            <a>
              
                    
            <span>

            <span>
              =
             []

      <code>

      <code>

    <p>
      The 
      <code>
        out
       variable is gone, and note that I’ve also moved
the return value to a new 
      <code>
        finish
       method, which converts the
incomplete tree to the final, complete tree. So: how do we add things to
the tree?
    

    <div>
      

      <p>
        HTML derives from a long line of document processing systems. Its
predecessor, 
        <a
href="https://en.wikipedia.org/wiki/Standard_Generalized_Markup_Language">
          SGML
        ,
traces back to 
        <a
href="https://en.wikipedia.org/wiki/TYPSET_and_RUNOFF">
          RUNOFF
         and is
a sibling to 
        <a>
          troff
        , now used for Linux
manual pages. The 
        <a
href="https://www.iso.org/committee/45374.html">
          committee
         that
standardized SGML now works on the 
        <code>
          .odf
        ,

        <code>
          .docx
        , and 
        <code>
          .epub
         formats.
      

    

    <h1>
      Constructing the Tree
    

    <p>
      Let’s talk about adding nodes to a tree. To add a text node we add it
as a child of the last unfinished node:
    

    <div>
      
      <pre
class="sourceCode>

    <p>
      Ok, that’s all done. Let’s test our parser out and see how well it

    <div>
      

      <p>
        The ill-considered JavaScript 
        <code>
          document.write
         method
allows JavaScript to modify the HTML source code while it’s being
parsed! This is actually a 
        <a
href="https://developer.mozilla.org/en-US/docs/Web/API/Document/write">
          bad
idea
        . An implementation of 
        <code>
          document.write
         must have the
HTML parser stop to execute JavaScript, but that slows down requests for
images, CSS, and JavaScript used later in the page. To solve this,
modern browsers use 
        <a
href="https://developer.mozilla.org/en-US/docs/Glossary/speculative_parsing">
          speculative
parsing
         to start loading additional resources even before parsing is
done.
      

    

    <h1>
      Debugging a Parser
    

    <p>
      How do we know our parser does the right thing—that it builds the
right tree? Well the place to start is 
      <em>
        seeing
       the tree it
produces. We can do that with a quick, recursive pretty-printer:
    

    <div>
      
      <pre
class="sourceCode>

          <span>
            
            <a>

             print_tree(node, indent
            <span>

            <span>

            (
            <span>

            <span>
              *
             indent, node)
          

          <span>
            
            <a>
              
                
            <span>
              for
             child 
            <span>
              in
             node.children:
          

          <span>
            
            <a>
              
                    print_tree(child, indent 
            <span>
              +
             
            <span>
              2
            )

    <p>
      Of course, there are more rules for handling malformed HTML:
formatting tags, nested paragraphs, embedded Scalable Vector Graphics
(SVG) and MathML, and all sorts of other complexity. Each has
complicated rules abounding with edge cases. But let’s end our
discussion of handling author errors here.
    

    <p>
      The rules for malformed HTML may seem arbitrary, and they are: they
evolved over years of trying to guess what people “meant” when they
wrote that HTML, and are now codified in the 
      <a
href="https://html.spec.whatwg.org/multipage/parsing.html">
        HTML parsing

      . Of course, sometimes these rules “guess” wrong—but as so
often happens on the web, it’s more important that every browser does
the 
      <em>
        same
       thing, rather than each trying to guess what the

      <em>
        right
       thing is.

    <h1>
      Exercises
    

    <p>
      4-1 
      <em>
        Comments
      . Update the HTML lexer to support comments.
Comments in HTML begin with 
      <code>
        <!--
       and end with

      <code>
        -->
      . However, comments aren’t the same as tags: they can
contain any text, including left and right angle brackets. The lexer
should skip comments, not generating any token at all. Check: is

      <code>
        <!-->
       a comment, or does it just start one?
    

    <p>
      4-2 
      <em>
        Paragraphs
      . It’s not clear what it would mean for one
paragraph to contain another. Change the parser so that a document like

      <code>
        <p>hello<p>world</p>
       results in two
sibling paragraphs instead of one paragraph inside another; real
browsers do this too. Do the same for 
      <code>
        <li>
       elements,
but make sure nested lists are still possible.
    

    <p>
      4-3 
      <em>
        Scripts
      . JavaScript code embedded in a

      <code>
        <script>
       tag uses the left angle bracket to mean
“less than”. Modify your lexer so that the contents of

      <code>
        <script>
       tags are treated specially: no tags are
allowed inside 
      <code>
        <script>
      , except the

      <code>
        </script>
       close tag.
      <span
class="note-container">
        
        <span>
          Technically it’s just

          <code>
            </script
           followed by a 
          <a
href="https://html.spec.whatwg.org/multipage/parsing.html#script-data-end-tag-name-state">
            space,
tab, 
            <code>
              \v
            , 
            <code>
              \r
            , slash, or greater than sign
          .
If you need to talk about 
          <code>
            </script>
           tags inside
JavaScript code, you have to split it into multiple
strings.
        
      
    

    <p>
      4-4 
      <em>
        Quoted attributes
      . Quoted attributes can contain spaces
and right angle brackets. Fix the lexer so that this is supported
properly. Hint: the current lexer is a finite state machine, with two
states (determined by 
      <code>
        in_tag
      ). You’ll need more states.
    

    <p>
      4-5 
      <em>
        Syntax highlighting
      . Implement the

      <code>
        view-source
       protocol as in 
      <a
href="http.html#exercises">
        Exercise 1-5
      , but make it
syntax-highlight the source code of HTML pages. Keep source code for
HTML tags in a normal font, but make text contents bold. If you’ve
implemented it, wrap text in 
      <code>
        <pre>
       tags as well to
preserve line breaks. Hint: subclass the HTML parser and use it to
implement your syntax highlighter.
    

    <p>
      4-6 
      <em>
        Mis-nested formatting tags
      . Extend your HTML parser to
support markup like

      <code>
        <b>Bold <i>both</b> italic</i>
      .
This requires keeping track of the set of open text formatting elements
and inserting implicit open and close tags when text formatting elements
are closed in the wrong order. The bold/italic example, for example,
should insert an implicit 
      <code>
        </i>
       before the

      <code>
        </b>
       and an implicit 
      <code>
        <i>
       after
it.
